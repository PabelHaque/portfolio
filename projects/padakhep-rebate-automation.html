Case study 05 · Automation & data extraction

Special-Permission Tracking & Microzen Validation

Branch staff at a microfinance institution request loan waivers, rebates and settlements the way people actually communicate — in a WhatsApp group, in Bangla and English, mixed in with dozens of unrelated procedural asks. This system reads the export, keeps only the genuine financial concessions, records each one exactly once, and checks every member against the core banking system to catch the thing policy forbids: a new loan issued after a concession. It never infers an approval.

RoleSole designer and builder
Year2026
Scope5 concession types (waiver, rebate, settlement, case withdrawal, write-off) · Bangla + English · 6-sheet audit workbook
StackPython, Flask, SQLite, Playwright (Chromium), Chart.js dashboard, Excel and JSON export, CLI for scheduled runs
CodePrivate repository — walkthrough available on request

The problem

A loan concession is a financial decision with a paper trail — except that here the paper trail was a group chat. Applications arrived as free-text messages, sometimes in Bangla, sometimes in English, often both, alongside requests that look similar but are not concessions at all: early disbursement, tenure extension, ceiling increases, savings-rate changes. Keeping track meant someone reading the whole chat.

Worse, the concession itself is only half the rule. The other half is that a member who has been granted one should not quietly receive a new loan afterwards — and that fact lives in a different system entirely, the institution's core banking software.

What I built

A locally hosted pipeline from chat export to audited ledger, with the core-banking check built in rather than left to whoever remembers to look.

  • A bilingual extractor that recognises the five concession types in either language and deliberately ignores the procedural requests that share their vocabulary.
  • Idempotent ingestion. Every upload re-reads the whole export, but an application is inserted only if its content hash — timestamp, sender, member ID, amount, loan date — is new. Re-uploading adds nothing; older messages obtained later from the group admin are inserted correctly even though they predate everything already stored.
  • Microzen validation through Playwright: log in once, open the member's record, collect every loan, visit each loan's detail page — disbursement date, principal, service charge, outstanding, overdue, approval, both guarantors — and flag any loan disbursed after the permission date as a policy violation.
  • A dashboard of KPIs, monthly trends, zone / branch / relationship-manager breakdowns and waiver exposure, plus a six-sheet Excel workbook — database, summary, risk-flagged members, pending review, RM summary, validation results — and JSON export.
  • A command-line path for scheduled runs, incremental by default; credentials live in a git-ignored config or environment variables, never in the repository.

The detail I would defend in an interview

No approval is guessed — by design, not by omission.

In the chat, approvals arrive as bare acknowledgements — a one-word reply from the approver, some time after some application. The tempting shortcut is obvious: attach each "okay" to the nearest preceding application and mark it approved. It would make the dashboard look complete on day one.

It would also, sooner or later, mark the wrong member's waiver as approved — a financial record that is wrong in a way nobody would notice until it mattered. So the system does not do it. Every application is stored as pending, and the decision is set by a person, per record, in the member's detail view. The dashboard has a "pending review" sheet precisely because that queue is real work, not a gap to be papered over by a heuristic.

The same instinct, on the matching side A member may have taken the same loan amount several times. To pin the concession to the right loan, the validator matches the WhatsApp message's disbursement date and amount — compared against both the principal and the total — rather than trusting either field alone. Where a match is ambiguous, it stays visible as ambiguous.

Two more decisions

  • Idempotency keyed on content, not position. Hashing timestamp + sender + member + amount + loan date means the pipeline is safe to re-run on the full export every time, which is exactly what a scheduled job needs — and it still accepts a back-filled history without a special import mode.
  • Read the record, not the summary. The validator visits every loan detail page rather than the member's overview, because the overview does not carry disbursement dates and guarantors, and the policy check is meaningless without the date.

Outcome

A chat that had to be read by hand is now a ledger with a review queue: each concession recorded once, tied to the exact loan in the core banking system, with every post-concession loan flagged automatically and a six-sheet audit workbook that finance can open directly. The approvals column is filled in by people — which is the point.
