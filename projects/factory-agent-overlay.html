Multi-Agent Software Factory

A drop-in overlay that converts any codebase into a governed software delivery pipeline run by 60 specialist agents — with four human approval gates that cannot be skipped, an adversarial critic that rejects work for being merely correct, and a verification rule that stops an agent from claiming a stage is finished when nothing was written to disk.

RoleSole designer and builder
Year2026 · actively maintained
Scale60 specialist agents · 20 workflow playbooks · 4 mandatory gates
StackPython, Claude Agent SDK, PowerShell, Bash, Pytest, JSON-manifest plugin packaging
CodePrivate repository — walkthrough available on request

The problem

Coding agents are fast and unreliable in a specific way: they will happily report that a stage is complete when nothing was produced, take a shortcut past the part of the work that needed judgement, and treat an unanswered question as permission to continue. Used ad hoc, the output looks plausible and the review burden lands entirely on the human — which is exactly the work you were trying to reduce.

I wanted the opposite arrangement: the agents do the volume, the process does the enforcing, and the human keeps the decisions that matter. Not a prompt library — a pipeline with teeth.

What I built

A portable overlay. You point it at an existing project, it installs a governance layer alongside your source — it never modifies the code it is installed into — and from that point the project has a structured delivery pipeline instead of an open chat window.

  • 60 specialist agents covering requirements, architecture, design, build, QA, security, documentation, deployment and business intelligence — including a six-agent technology-decision sub-pipeline that scores stack options against alternatives rather than defaulting to whatever is fashionable.
  • 20 workflow playbooks for the shapes work actually arrives in: bug fix, hotfix, schema change, data migration, security incident, UI enhancement, documentation-only, consulting engagement, new-system incubation, and a deliberate cosmetic_fast_path so a one-line CSS change does not have to walk the full pipeline.
  • Four mandatory human gates — CLARIFY, REQ, Mockup and PR.
  • An adversarial critic that issues a pass/revise verdict and blocks the pipeline on revise.
  • A write-guard hook at the harness level protecting registries, agent definitions, approved requirements and secrets from being edited by the agents themselves.

The pipeline, and where it stops

The interesting part is not the number of stages — it is the four places the pipeline hands control back to a person and refuses to continue without an answer.

The detail I would defend in an interview

Artifact verification — agents cannot mark their own homework.

The failure mode that makes agent pipelines untrustworthy is the confident false completion: a stage reports success, the next stage builds on nothing, and the error only surfaces four stages later when the context that would explain it is gone.

So stage completion is not a claim an agent is allowed to make. A stage is complete when a physical file exists at the expected path and passes a self-check for that artifact type. No file, no completion — regardless of what the agent reports. This moves the integrity check from the model's judgement, where it is unreliable, to the filesystem, where it is not.

Why this matters It is the difference between a pipeline that describes a quality process and one that is one. The same reasoning drives the write-guard hook: if an agent could edit the registry that defines the rules it is judged against, the rules would be advisory. It cannot, so they are not.

Two more decisions worth naming

  • Business rules and KPIs live in a registry, never in code. A formula duplicated across a backend, a report and a dashboard drifts. One definition, referenced everywhere, and changing it is a governed action.
  • Agent updates are themselves a governed workflow. Changing an agent needs a proposal, human approval, regression tests and a rollback path — the update_agents and sharpen_agents playbooks. The system that enforces process on your code is held to the same process.

Engineering the portability

An overlay is only useful if installing it is boring. It ships with parallel PowerShell and Bash installers plus matching verifiers, has no npm or pip install step of its own, and creates only directories and stub files. Alongside that there is a packaging script that assembles a Claude Code plugin distribution from the live agent, skill and hook directories — read-only sources, never mutated — with a dry-run mode that reports what it would write before it writes anything.

It runs on Windows and Unix, and there is a one-command setup path for moving the whole working environment to a new machine. That was not gold-plating: portability is what makes the thing an overlay rather than a bespoke configuration of one laptop.

Outcome

The overlay is installed in and drives the three other systems in this portfolio. The PMUK allocation engine, the reporting dashboard and the study platform were all built through it — which is the honest measure of whether it works: it is not a demo of a process, it is the process the rest of this work was produced by.
