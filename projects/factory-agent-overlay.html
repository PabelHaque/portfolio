Case study 01 · AI orchestration & platform

Multi-Agent Software Factory

Coding agents are fast and, left alone, confidently wrong. This overlay installs a delivery pipeline around any codebase — 71 specialist agents across 38 stages — and puts four gates in it where the work stops and waits for a person. A critic rejects output for being merely correct, and no agent can mark a stage done without a file on disk that passes its own check.

RoleSole designer and builder
Year2026 · actively maintained

The problem

Coding agents fail in a specific way: they report a stage complete when nothing was produced, shortcut the part of the work that needed judgement, and treat an unanswered question as permission to continue. Used ad hoc, the output looks plausible and the whole review burden lands back on the human.

The agents do the volume, the process does the enforcing, the human keeps the decisions.

What I built

A portable overlay. Point it at an existing project and it installs a governance layer alongside the source — never modifying the code it is installed into — and from that point the project has a structured delivery pipeline instead of an open chat window.

  • 71 specialist agents across requirements, architecture, design, build, QA, security, documentation, deployment and business intelligence — including a six-agent technology-decision sub-pipeline that scores stack options against alternatives.
  • 20 workflow playbooks for the shapes work actually arrives in: bug fix, hotfix, schema change, data migration, security incident, consulting engagement, new-system incubation — and a deliberate cosmetic_fast_path so a one-line CSS change does not walk the full pipeline.
  • Four mandatory human gates — CLARIFY, REQ, Mockup, PR.
  • An adversarial critic whose revise verdict blocks the pipeline.
  • A harness-level write-guard hook protecting registries, agent definitions, approved requirements and secrets from the agents themselves.

The pipeline, and where it stops

Thirty-eight stages, condensed below to the eleven that matter for the shape. The number is not the interesting part — the four places it hands control back to a person and refuses to continue without an answer are.

The detail I would defend in an interview

Artifact verification — agents cannot mark their own homework.

The confident false completion is what makes agent pipelines untrustworthy: a stage reports success, the next stage builds on nothing, and the error surfaces four stages later when the context that would explain it is gone.

So stage completion is not a claim an agent is allowed to make. A stage is complete when a physical file exists at the expected path and passes a self-check for that artifact type. No file, no completion — regardless of what the agent reports. The integrity check moves from the model's judgement, where it is unreliable, to the filesystem, where it is not.

Same principle, applied to the rules If an agent could edit the registry that defines the rules it is judged against, the rules would be advisory. The write-guard hook means it cannot, so they are not.

Two more decisions

  • Business rules and KPIs live in a registry, never in code. A formula duplicated across a backend, a report and a dashboard drifts. One definition, referenced everywhere; changing it is a governed action.
  • Agent updates are themselves a governed workflow. Changing an agent needs a proposal, human approval, regression tests and a rollback path — the update_agents and sharpen_agents playbooks. The system that enforces process on your code is held to the same process.

Portability

Parallel PowerShell and Bash installers with matching verifiers; no npm or pip install step of its own; creates only directories and stub files. A packaging script assembles a Claude Code plugin distribution from the live agent, skill and hook directories — read-only sources — with a dry-run mode that reports what it would write before writing anything. One-command setup for a new machine, Windows or Unix.

Outcome

The overlay drives the three other systems in this portfolio. The PMUK allocation engine, the reporting dashboard and the study platform were all built through it — it is not a demo of a process, it is the process the rest of this work was produced by.
