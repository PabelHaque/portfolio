Case study 06 · Data analysis & reporting

Reports & Analytics

For twenty-seven months I was the person who could answer any question about a microfinance loan book within a day, from one monthly export. Regulators wanted classification schedules; finance wanted a bank-ready disbursement statement; programme heads wanted to know which products and activities carried the overdue; donors wanted sector splits. The answers are 73 pandas notebooks — kept as they were written, checks included — and, later, a small library that defines each of the recurring numbers once.

RoleSole analyst — question in, numbers out, every month
PeriodOctober 2023 – January 2026
Scale104 notebooks written · 73 kept · 9,489 lines of pandas · 7 programmes · one dataset
StackPython, pandas, NumPy, JupyterLab, xlsxwriter / openpyxl, matplotlib / plotly, SQLAlchemy, ipywidgets; pytest and pre-commit for the library
CodePrivate repository — walkthrough available on request

The problem

The institution's MIS exports a monthly CM Report: one row per member-loan, about sixty Bangla-headed columns, several hundred thousand rows. It is the only complete picture of the loan book, and there was no BI layer on top of it. Every question — from the regulator's half-yearly return to "which branches disburse most in the last three days of the month?" — meant someone working the file by hand.

The file fights back. Dates arrive in four formats depending on which tool touched the export last. Member IDs and phone numbers lose their leading zeros the moment Excel opens them. Headers carry stray whitespace. A member with three loans appears on three rows, so a naive count triples them. And the fiscal year runs July to June, so "2023-2024" has to be derived, never read.

What I built

Seven programmes of analysis, each answering a different kind of question, all starting from the same cleaning steps.

The detail I would defend in an interview

The checks stay in the code.

Scattered through the notebooks are lines like file['compulsory_withdrawn'].sum() - (rsp_w_returned.sum() + rsp_m_returned.sum()) — an expression whose only correct value is zero — and df[df['member_id'].duplicated(keep=False)], a look at exactly the rows that would double-count if forgotten. Many are commented out; they were run, satisfied, and left in place.

When these notebooks went into version control I was tempted to tidy them away. I didn't. They are the record of how each number was verified before it went to a regulator or a finance team, and they are the difference between "the total is 17,962" and "the total is 17,962 and here is why I believe it." A clean notebook with no checks is not more professional; it is less auditable.

What did change The definitions that every notebook re-implemented — the four-format date parser, the July–June fiscal year, total savings, PAR, the MRA and MAPLE classification bands, the activity-to-sector taxonomy, the split-into-workbooks-with-subtotals step — now live once, in a small library with tests against a synthetic export. New analysis imports them. Old analysis stands as written.

Two more decisions

  • Organised by question, not by who asked. The working folders were named after requesters. The repository is grouped into the seven programmes above, so a reader finds every PAR analysis in one place regardless of which manager commissioned it.
  • Sanitised by pipeline, not by hand. 104 notebooks carried rendered outputs with member data, absolute paths from two laptops, a database connection string and identifiers in notes. A scrubber clears outputs, rewrites paths to two environment-driven folders, replaces the connection string with an environment variable and redacts identifiers — and runs as a pre-commit check so nothing regresses. The same scrubber turned a 32 MB folder of private output into a repository that can be shown.

Outcome

Twenty-seven months of questions answered from one file, now organised so the next person can find and rerun them; a shared library that makes the recurring numbers consistent by construction; and the data understanding that the later systems in this portfolio — the target-allocation engine, the reporting dashboard, the special-permission tracker — were built on.
