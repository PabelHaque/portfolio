AK47 Performance & Reporting Dashboard

Performance data in a field network is needed by nearly everyone and should be seen whole by almost no one. This dashboard gives a five-tier hierarchy one interface and five different views of it — each tier exactly one level wider than the one below — plus the reporting suite that replaced hand-assembled scorecards, transfer analytics and HR exports.

RoleSole designer and builder
Year2026
StackDjango REST backend, Next.js + TypeScript frontend, PostgreSQL in Docker, one-click local launcher
AudienceField staff, branch managers, area managers, regional managers, head office — plus a separate admin console
ReportingHO/HR export · annual scorecard · transfer tracking & analytics · leaderboard
CodePrivate repository — walkthrough available on request

The problem

Performance data in a branch network has an awkward property: almost everyone needs it, and almost nobody should see all of it. A field officer looking at a colleague's figures is a personnel problem. A regional manager who can only see their own numbers cannot do their job. Head office needs the whole picture in a format payroll and HR can consume.

One dashboard with a set of filters is a data-exposure incident waiting for someone to bookmark the wrong URL. Scoping has to be a property of the account, enforced server-side — not a view the client chooses.

The visibility model

Each tier sees exactly one level wider than the one below it.

TierSees
Field staffTheir own figures only
Branch managerEvery officer in their branch
Area managerEvery branch in their area
Regional managerEvery area in their region
Head officeThe network, plus the HR and payroll exports
AdminScoring configuration and reporting access — a separate console, not a super-powered dashboard

The admin console is separate on purpose. The account that can change how scoring works is not the account that browses performance data, so a configuration mistake and a data-access mistake cannot be made in the same session by the same click.

The detail I would defend in an interview

An auth guard that matched too much, and the endless login loop it caused.

During the build, the login page began reloading itself forever in development. The symptom pointed at authentication — a redirect loop between login and dashboard — and that is where an hour could easily have gone.

The actual cause: the auth check was intercepting the Next.js dev server's hot-module-reload websocket and redirecting it. The browser lost its HMR channel, reconnected, got redirected again, and reloaded on every cycle. Nothing was wrong with the credentials, the session, or the redirect logic in the sense the symptom suggested.

What I took from it A route guard is a matcher, and a matcher's blast radius is everything it did not mean to match. The bug was not in the authentication logic — it was in the breadth of the pattern the logic was attached to. No amount of staring at auth code would have shown a websocket being redirected; reading the transport did.

Reporting that replaced manual assembly

  • HO / HR export — the network view in the shape payroll and HR consume.
  • Annual scorecard — a year of performance per staff member, consistent across tiers because it is computed from one definition rather than re-derived per report.
  • Transfer tracking & analytics — staff movement between branches and areas over time; exactly the history that gets lost in per-branch spreadsheets.
  • Leaderboard — comparative standing, visible only within the scope the viewer's tier already grants.

Scoring configuration lives in the admin console, so the formula behind a scorecard is a governed setting rather than a constant buried in a report query — the same registry principle as the target system and the agent factory.

Runnable by someone who is not me

The whole local stack — database container, Django backend, Next.js frontend, browser — comes up from a single launcher, with the manual two-terminal path documented underneath. The troubleshooting section is written against failures that actually occurred, including the websocket loop above and a local database role whose password had drifted from the documented value: the error message ("password authentication failed") names none of the four plausible causes, so the doc does.

Where it sits in the wider system

The dashboard shares its field hierarchy with the PMUK target system and consumes that system's exports, so a target set through the cascade engine and the performance measured against it describe the same staff member, branch and cycle. The target system has a dedicated integration module for this boundary rather than the two systems reaching into each other's tables.

Outcome

Delivered through the agent factory's full pipeline — code review, a three-round QA cycle, then security, consistency and documentation stages before the final human approval gate. Reporting that took manual assembly per cycle now runs as four scoped views and an export, against data every tier sees exactly as much of as their role permits.
