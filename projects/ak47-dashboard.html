AK47 Performance & Reporting Dashboard

The reporting half of the field-operations story. Where the target system decides what each officer owes, this dashboard shows what everyone actually did — with visibility scoped strictly by position in a five-tier hierarchy, and a reporting suite that produces the annual scorecards, transfer analytics and HR exports that were previously assembled by hand.

RoleSole designer and builder
Year2026
StackDjango REST backend, Next.js + TypeScript frontend, PostgreSQL in Docker, containerised local dev with a one-click launcher
AudienceField staff, branch managers, area managers, regional managers, head office — plus a separate admin console
ReportingHO/HR export · annual scorecard · transfer tracking & analytics · leaderboard
CodePrivate repository — walkthrough available on request

The problem

Performance data in a branch network has an awkward property: almost everyone needs it, and almost nobody should see all of it. A field officer looking at a colleague's figures is a personnel problem. A regional manager who can only see their own numbers cannot do their job. Head office needs the whole picture in a format payroll and HR can actually consume.

Solve that with one dashboard and a set of filters and you have built a data-exposure incident waiting for someone to bookmark the wrong URL. The scoping has to be a property of the account, enforced server-side, not a view the client chooses.

The visibility model

Each tier sees exactly one level wider than the one below it.

TierSees
Field staffTheir own figures only
Branch managerEvery officer in their branch
Area managerEvery branch in their area
Regional managerEvery area in their region
Head officeThe network, plus the HR and payroll exports
AdminScoring configuration and reporting access — a separate console, not a super-powered dashboard

Separating the admin console from the dashboard was deliberate. The account that can change how scoring works is not the account that browses performance data; keeping them apart means a configuration mistake and a data-access mistake cannot be made in the same session by the same click.

The detail I would defend in an interview

An auth guard that matched too much, and the endless login loop it caused.

During the build, the login page began reloading itself forever in development. The symptom pointed at authentication — a redirect loop between the login route and the dashboard — and that is where an hour could easily have gone.

The actual cause was that the auth check was intercepting the Next.js dev server's hot-module-reload websocket connection and redirecting it. The browser lost its HMR channel, reconnected, got redirected again, and the page reloaded on every cycle. Nothing was wrong with the credentials, the session, or the redirect logic in the sense the symptom suggested.

What I took from it A route guard is a matcher, and a matcher's blast radius is everything it did not mean to match. The bug was not in the authentication logic — it was in the breadth of the pattern the logic was attached to. Since then I treat "what else does this match?" as part of writing the guard, not as something to discover from a symptom three layers away. It is also a case for reading the transport, not just the application: no amount of staring at auth code would have shown a websocket being redirected.

The environment lesson alongside it

The same build surfaced a local database whose role password had drifted from the documented value, so the backend could not authenticate. It was a disposable local dev container, and the fix was one command — but the documentation now names the symptom, the cause, and the recovery command explicitly, because the error message ("password authentication failed") tells you nothing about which of the four plausible causes you are looking at. Documenting the failure you actually hit is worth more than documenting the happy path a third time.

Reporting that replaced manual assembly

  • HO / HR export — the network view in the shape payroll and HR consume, rather than a screenshot of a dashboard pasted into a workbook.
  • Annual scorecard — a year of performance per staff member, consistent across tiers because it is computed from one definition rather than re-derived per report.
  • Transfer tracking & analytics — staff movement between branches and areas over time, which is precisely the history that gets lost when performance is tracked in per-branch spreadsheets.
  • Leaderboard — comparative standing, visible only within the scope the viewer's tier already grants.

Scoring configuration lives in the admin console, so the formula behind a scorecard is a governed setting rather than a constant buried in a report query — the same registry principle that runs through the target system and the agent factory.

Built to be run by someone who is not me

The whole local stack — database container, Django backend, Next.js frontend, browser — comes up from a single launcher script, with the manual two-terminal path documented underneath for when something needs to be taken apart. There is a troubleshooting section written against the failures that actually occurred, including the one above.

That matters more than it sounds. A system nobody else can start is a system nobody else can review, and an internal tool that only runs on its author's machine has a very short useful life.

Where it sits in the wider system

The dashboard shares its field hierarchy with the PMUK target system and consumes that system's exports, so a target set through the cascade engine and the performance measured against it describe the same staff member, the same branch, and the same cycle. The target system has a dedicated integration module for this boundary rather than the two systems reaching into each other's tables.

Outcome

Delivered through the agent factory's full pipeline — code review, a three-round QA cycle, then security, consistency and documentation stages before the final human approval gate. Reporting that took manual assembly per cycle now runs as four scoped views and an export, against data every tier is allowed to see exactly as much of as their role permits.
