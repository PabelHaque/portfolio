Case study 02 · Enterprise system & allocation engine

PMUK Field-Staff Target & Budget Allocation System

A branch gets a target. Somebody has to turn it into a number for every field officer — fairly, across 409 branches and 2,574 staff, every planning cycle, with nobody able to argue the arithmetic. This engine does it with a weighted largest-remainder cascade, and refuses to run on anything it could not reproduce: the same inputs give the same 17,962 numbers, bit for bit.

The problem

A branch is told to grow its savings balance by a certain amount. That figure has to be split across the branch's field officers, and splitting it evenly is unfair in a way everyone can see: one officer holds three times the loan outstanding of the next; another covers twice the member count.

Weighting the split by each officer's own portfolio raises three harder problems at once:

  • The parts must sum to the whole. Weighted division produces fractions. Round each share independently and the officer targets no longer add up to the branch target — and a planning system whose numbers do not reconcile is worse than a spreadsheet, because it looks authoritative.
  • Different metrics need different weightings. Overdue recovery should be distributed on each officer's overdue book. Savings growth should not.
  • The same inputs must produce the same outputs. When an officer asks why their number changed, "the engine ran again" is not an acceptable answer.

The allocation engine

A weighted largest-remainder cascade.

Each officer gets a score from their own portfolio indicators — samity count, member count, loan outstanding — combined through a weight matrix. Scores become proportional shares of the branch target. Those shares are rounded by the largest-remainder method: floor every share, count the whole units left unallocated, hand them out one at a time to the officers with the largest fractional remainders.

The officer targets always foot exactly to the branch target, and nobody's proportional share is distorted by more than one unit. It is the same family of method used to apportion legislative seats to populations, for the same reason: you cannot give someone 0.6 of a seat, and the total is fixed.

The detail I would defend in an interview

Determinism is enforced, not hoped for.

Largest-remainder allocation is order-sensitive at the margin. Two officers with identical remainders and one unit left: whoever the engine reaches first receives it. If input ordering can vary between runs — and in a database it can, unless you make it not — the same inputs legitimately produce different outputs.

The fix is structural. Every indicator carries an ordinal: a fixed, unique position in a canonical order. The engine refuses to run unless indicators arrive strictly increasing by ordinal. Not a warning — a refusal. That is what makes a re-run bit-identical.

  • Ordinals are spaced in gaps of ten, so a new indicator can be inserted later without renumbering.
  • Changing an ordinal never changes a number. Weights are keyed by indicator identity, never by position — re-ordering the matrix rows is a display change, not a data change. Getting this wrong would let a cosmetic edit silently rewrite everyone's targets.
The independence property Each metric column in the weight matrix is its own weight set that must sum to exactly 1.000000. That is what answers "can we weight overdue differently?" — put overdue outstanding at 1.0 in that column and zero elsewhere, and overdue distributes purely on each officer's overdue book while every other metric is untouched. A zero weight is provably inert: it never enters the candidate set, never triggers an exclusion, never contributes to a score.

Business rules that took judgement

A metric may be cascaded or displayed, never both

Savings-balance increase is the sum of three product lines. Cascade the three products, or display the roll-up — cascading both would target the same work twice and quietly double a team's obligations. The system refuses the combination outright.

Direction is required, with no default

Every metric must declare its direction, and the form ships with nothing pre-selected. That is what lets the system tell a legitimate large negative on an overdue-recovery metric from a nonsensical negative on a growth metric. A pre-filled radio would make that decision silently, on the one field where a wrong default is most expensive.

New configuration never moves existing numbers

Adding an indicator seeds a zero-weight row into every existing weight configuration, and the form reports how many rows it seeded. Nothing already agreed shifts until a weight is deliberately assigned. The related risk — an indicator whose spreadsheet column heading changed upstream and now silently contributes nothing at import — is surfaced by listing unmapped indicators first and counting them in the picker title.

Access control that fails closed

Roles are scoped to positions in the org hierarchy, and scope is assigned explicitly. A scoped account with no branches assigned sees nothing, and the interface says so plainly rather than rendering an empty state that looks like a bug. It does not fall back to showing everything — and saying so in the UI is what stops an operator from "fixing" it by widening someone's access.

The cycle

1. Upload staff information  ──►  who is where, and their portfolio
2. Load branch targets       ──►  what each branch must achieve
   (1 and 2 are independent; both required before 3)
3. Compute                   ──►  cascade branch targets across staff
4. Finalise                  ──►  freeze the run
5. Export                    ──►  workbooks for downstream use

The weight-matrix editor balances itself as you work: every other cell offers the exact remaining share as a one-click fill, the last empty cell completes itself so the column closes at 1.000000, and the sum line reports how far short you are.

Outcome

One planning cycle: 17,962 individual staff targets across 409 branches from branch-level inputs — reconciling exactly, reproducible on demand, an audit trail behind each figure, a bilingual interface for the field.
