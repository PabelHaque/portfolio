Case study 06 · Automation & verification

Special Rebate Verification & Member Notification

Nineteen zonal offices email spreadsheets of members who have been granted a special rebate. Each row has to reach the master file exactly once, be checked against the loan system, be tested against the rebate formula, and become an SMS to the member. This automates all four and then stops: the Outlook message it produces is a draft. Money leaving the institution and a text arriving on a member's phone are both irreversible, so a person presses send.

The problem

A special rebate is a discretionary reduction granted to a member who has repaid. The request arrives as an email from a zonal admin office with a spreadsheet attached, in the same layout as the master file that finance keeps. Someone then has to open each attachment, copy the new rows into the master workbook, look every member up in the loan system to confirm the loan really is fully repaid and find the last payment, apply the rebate formula, write the Bangla SMS text, and hand the result to the ICT team to send.

Every step of that is a place to make an expensive mistake. The same member appended twice is a rebate paid twice. A rebate computed from the wrong base is money out of the door. An SMS to someone who was never eligible is a promise the institution then has to honour or retract. And the master file is the only record, so a bad paste is permanent.

What I built

One command runs the whole cycle for a date range, and every stage can be run on its own while something is being checked.

The detail I would defend in an interview

The unsent draft is the product, not a limitation.

It would have been three lines to send the mail. I did not, and the module that builds it is named for what it does rather than what it could do. Two irreversible things happen at the end of this pipeline: an institution pays out money, and a member receives a message saying so. Neither can be recalled if the formula was wrong, and the formula is exactly the part I was least certain about.

Uncertainty belongs in configuration, not in code The rebate rate and the base it applies to live in a settings file, with a note in the documentation saying they must be confirmed with management before a production run. Encoding a number I had not had confirmed as though it were settled would have hidden the one thing a reviewer most needed to see.

Two more decisions

  • Back up before you append, not after. The master workbook is the institution's record of every rebate granted. The backup is written before a single row is added, so the worst outcome of a bad run is a file to restore rather than a history to reconstruct.
  • An audit database beside the workbook. Four tables record every email processed, every row extracted, every verification result and every append. The workbook is what finance opens; the database is what answers "why is this member in here twice" six months later.

Outcome

A cycle of copying between mailboxes and spreadsheets is now one run that ends in a draft waiting for a human to read. The rows are unique by construction, every member has been checked against the loan system rather than taken on trust, and the reasoning behind each decision is queryable long after the workbook has moved on.
